## 一、必须修改项（Blocking）

### B-01：状态机用例的 API 造数方案未验证，5 条迁移用例前置条件不可行

**问题描述：** F-TC-025~F-TC-029 共 5 条订单状态机用例的前置条件依赖通过 API 将订单状态修改为"已支付"等非初始状态。但系统探索报告中**没有任何已验证的 API 端点**能直接修改订单状态。用例中自行推测了 `PUT /api/orders/{orderId}` 或 `PATCH /api/orders/{orderId}/status` 两种格式，均为**未经验证的推断**。

**所在位置：** F-TC-025（步骤4）、F-TC-026（步骤5）、B-TC-012（测试数据）

**证据：**
- 系统探索报告 F-18 仅验证了订单创建 API（POST），未验证订单状态修改 API
- 用例中明确写道"尝试多种 API 格式"——说明编写者自己也不确定哪个可用
- B-TC-012 的测试数据部分直接假设了 API 格式，但无事实支持

**影响：** 如果 API 造数方案不成立，5 条状态机 PO 级用例全部无法执行，本轮核心验证目标（状态机 5 迁移）完全落空。

**严重度：** 高
**责任阶段：** 设计

**修改建议：**
1. **在用例执行前先进行 API 探针测试**：新增一条前置用例，专门验证 `PUT /api/orders/{id}` 和 `PATCH /api/orders/{id}/status` 是否可用，请求体格式是什么
2. **备选造数路径**（按优先级排列）：
   - **方案A**：前端页面操作——如果系统有模拟支付功能（如"去支付"按钮直接跳转成功），通过页面操作完成状态迁移
   - **方案B**：数据库直连——直接 UPDATE orders 表的 status 字段（需确认数据库访问权限）
   - **方案C**：种子数据预置——在测试环境初始化时直接插入各状态的订单数据
   - **方案D**：后台管理操作——如果 S-02（操作列为空）被修复，通过后台"发货"等按钮操作
3. 每条状态机用例的前置条件应写明：**"如 API 方案不可用，使用方案X作为降级路径"**

---

### B-02：状态机用例存在链式依赖，非独立可执行

**问题描述：** F-TC-025→F-TC-026→F-TC-027 形成严格顺序链（待支付→已支付→已发货→已完成），F-TC-029 也依赖 F-TC-025 的产出。但用例文档未标注执行顺序约束，且 F-TC-029 与 F-TC-026 共用同一笔"已支付"订单——**如果 F-TC-029 先执行（将订单改为已退款），F-TC-026 将因前置条件不满足而失败**。

**所在位置：** F-TC-025~F-TC-029、前台用例文档整体

**证据：**
- F-TC-026 前置条件："有一笔'已支付'状态的订单（需先完成 F-TC-025）"
- F-TC-029 前置条件："有一笔'已支付'状态的订单（需先完成 F-TC-025）"
- 两者共用同一笔订单，但状态迁移方向不同（一个→已发货，一个→已退款）

**影响：** 用例无法独立执行，并行执行时互相污染，测试结果不可靠。

**严重度：** 高
**责任阶段：** 设计

**修改建议：**
1. **为 F-TC-029 创建独立的"已支付"订单**，不与 F-TC-026 共用。具体：F-TC-025 验证完"待支付→已支付"后，**再创建一笔新订单并将其推到"已支付"状态**，专供 F-TC-029 使用
2. 在用例文档中增加**执行顺序约束表**，明确标注：
   - F-TC-025 必须在 F-TC-026、F-TC-028、F-TC-029 之前执行
   - F-TC-026 必须在 F-TC-027 之前执行
   - F-TC-026 和 F-TC-029 需要各自独立的"已支付"订单
3. 每条用例的"测试数据"字段应写明具体的订单来源，而非仅写"需先完成 F-TC-025"

### B-03：F-TC-020（重复提交订单）标记为"探索性"但应为正式验证项

**问题描述：** 用户明确要求覆盖"bug复现×2"，其中一项是"重复提交订单"（B-R02）。但 F-TC-020 的可观察预期全部标记为【探索性】，有 2 个候选预期，没有确定性预期。作为用户明确要求的 PO 级验证项，预期不应是"候选"。

**所在位置：** F-TC-020 可观察预期字段

**证据：**
- 测试点 F-TP-045 优先级为 PO，来源标注为"用户要求①"
- 需求理解文档 §3.2 将"重复提交订单"列为异常维度风险点，优先级 PO
- 但用例预期写了"候选预期A（理想）""候选预期B（缺陷）"——这不是验证，是探索

**影响：** 测试执行时无法判定 Pass/Fail，PO 级用例失去验收意义。

**严重度：** 高
**责任阶段：** 设计

**修改建议：**
1. 将 F-TC-020 的预期**拆分为两个子场景**：
   - **F-TC-020a（防护验证）**：预期为"仅创建 1 笔订单，按钮点击后立即 disabled"——这是理想行为，如果 Pass 说明防护有效
   - **F-TC-020b（缺陷复现）**：如果 F-TC-020a Fail（创建了多笔），则记录为 Bug 复现成功
2. 明确标注：F-TC-020 的核心目标是**验证防重复提交机制是否存在**，而非探索"会怎样"

### B-04：F-TC-036 清理责任依赖手动恢复，存在数据污染风险

**问题描述：** F-TC-036（修改个人信息保存）的清理责任为"测试完成后将昵称和邮箱恢复为原始值（昵称: '张三'，邮箱: 'zhangsan@test.com'）"。这是一个**手动清理步骤**，如果测试执行中断或清理遗忘，buyer1 的个人信息将被永久修改，影响所有后续依赖 buyer1 数据的用例。

**所在位置：** F-TC-036 清理责任字段

**证据：**
- buyer1 是前台测试的主力账号，被 F-TC-002/005/012/014/015/016/017/018/020/021/022/023/024/025~030/034~039/040 等大量用例使用
- 如果昵称被改为"张三-测试修改"，F-TC-002 的预期"导航栏显示'张 张三'"将 Fail

**影响：** 清理失败将导致后续用例级联失败，且难以定位原因。

**严重度：** 高
**责任阶段：** 设计

**修改建议：**
1. **调整执行顺序**：将 F-TC-036 放在 buyer1 相关用例的**最后执行**（登出之前）
2. **增加清理验证步骤**：清理后增加一步验证——刷新页面确认昵称恢复为"张三"
3. **降级方案**：如果清理失败，记录为环境问题而非用例失败

## 二、建议修改项（Should）

### S-01：F-TC-040（buyer2 完整流程）粒度过大，应拆分

**问题描述：** F-TC-040 将 buyer2 的 14 个步骤压缩为一个用例，预期为"每一步与 buyer1 一致"。这个用例预计执行时间超过 30 分钟，任何一步失败都需要从头重跑。

**所在位置：** F-TC-040

**证据：** 用例步骤涵盖登录、浏览、搜索、详情、加购、购物车、结算、下单、地址管理、收藏、个人信息、登出——这是 12 个独立功能的端到端测试。

**影响：** 执行效率低，失败定位困难，无法并行。

**严重度：** 中
**责任阶段：** 设计

**修改建议：**
1. 将 F-TC-040 拆分为 3-4 个独立用例：
   - F-TC-040a：buyer2 购物核心流程（登录→浏览→加购→结算→下单→取消）
   - F-TC-040b：buyer2 数据管理（地址 CRUD、收藏管理）
   - F-TC-040c：buyer2 个人信息与登出
   - F-TC-040d：buyer2 订单详情收货信息验证（重点对比 buyer1 的 S-01 问题）
2. 每个子用例独立清理，不依赖其他子用例的执行结果

---

### S-02：F-TC-013（库存为0加入购物车）依赖后台用例 B-TC-003，但依赖关系未显式声明

**问题描述：** F-TC-013 的测试数据写道"需通过后台创建一个库存为0的测试商品（见后台用例 B-TC-003），或找到库存为0的规格组合"。但 B-TC-003 是"新增商品必填字段校验"用例，**并非创建库存为0的商品**。这是一个**交叉引用错误**。

**所在位置：** F-TC-013 测试数据字段

**证据：**
- B-TC-003 的场景名称是"新增商品必填字段为空时保存的校验"，测试数据为空表单
- F-TC-013 需要的是一个库存为0的商品，但系统探索报告中**未发现任何库存为0的商品**（F-05 显示 iPhone 15 Pro Max 库存为 69/3）

**影响：** 前置条件无法满足，用例无法执行。

**严重度：** 中
**责任阶段：** 设计

**修改建议：**
1. **新建一个专用用例**（如 B-TC-003b）：通过后台新增商品功能创建一个库存为0的测试商品
2. 或者：在 F-TC-013 的前置条件中明确写明"通过后台新增商品，基础库存设为0，状态设为'上架'"
3. 更新交叉引用：将"见后台用例 B-TC-003"改为正确的用例编号

---

### S-03：F-TC-022（多商品结算）测试数据不具体

**问题描述：** F-TC-022 的测试数据写道"商品2: 需从其他分类选择一件商品（如 Samsung 或 AirPods）"——这是一个**模糊指示**，执行者需要自行决定选哪个商品、哪个规格组合。

**所在位置：** F-TC-022 测试数据字段

**证据：** 系统探索报告 F-04 显示手机数码分类有 5 件商品，但未记录每件商品的规格和价格。执行者无法确定"Samsung"应该选哪个规格组合、价格是多少。

**影响：** 不同执行者可能选择不同商品，导致预期金额无法预先计算，测试不可重复。

**严重度：** 中
**责任阶段：** 设计

**修改建议：**
1. 明确指定商品2：**"Samsung Galaxy S24（如存在），选择任意可用规格组合"**
2. 或者：在用例中增加一步"记录商品2 的单价"，预期改为"合计 = 商品1单价×数量1 + 商品2单价×数量2"
3. 预期金额不应硬编码为具体数值，而应写为"等于各商品小计之和"

---

### S-04：探索性用例的"候选预期"应统一标注为"观察目标"而非"预期"

**问题描述：** 多条用例（F-TC-008/013/019/020/021/025/026/027/028/029/038）的可观察预期字段包含【探索性】标注和"候选预期A/B/C"。这些"候选预期"在测试执行时**无法判定 Pass/Fail**，因为执行者不知道哪个是"正确"的。

**所在位置：** 前台用例中所有标记为【探索性】的用例

**证据：** 测试评审标准要求"预期结果是否具体、可观察、可验证"。候选预期不满足"可验证"要求。

**影响：** 探索性用例的测试结果只能记录"观察到X"，无法产出 Pass/Fail 结论。

**严重度：** 中
**责任阶段：** 设计

**修改建议：**
1. 将"可观察预期"字段拆分为两个子字段：
   - **观察目标**：描述要验证什么（如"确认防重复提交机制是否存在"）
   - **记录要求**：描述需要记录什么信息（如"记录创建了几笔订单、按钮是否 disabled"）
2. 探索性用例的判定标准应为"是否收集到足够信息"而非"是否符合某个候选预期"

---

### S-05：前台测试点中注册边界用例（F-TP-002~008）未转化为用例

**问题描述：** 前台测试点清单中 F-TP-002~F-TP-008 共 7 个注册相关测试点（用户名为空、少于3字符、超过50字符、密码少于6位、确认密码不一致、已存在用户名、选填字段留空），但用例文档中**仅有 F-TC-001（正常注册成功）一条注册用例**。

**所在位置：** 前台用例文档 §1 用户注册与登录

**证据：**
- 测试点 F-TP-002~008 优先级为 P1/P2，属于"重要功能验证"
- 用例文档中无对应的 F-TC-xxx 用例

**影响：** 注册功能的异常和边界场景未被覆盖，但这些属于 P1/P2 级别，不阻塞本轮核心验证。

**严重度：** 中
**责任阶段：** 设计

**修改建议：**
1. 评估是否需要在本轮覆盖注册边界用例——如果时间紧张可推迟到下一轮
2. 如需覆盖，新增 F-TC-001a~001e 用例，覆盖 F-TP-002~008 中的 P1 级测试点
3. 如不覆盖，在用例文档中明确标注"注册边界用例（F-TP-002~008）不在本轮执行范围"

### S-06：后台 B-TC-005/006（下架/上架）使用种子数据商品，违反"不修改种子数据"原则

**问题描述：** B-TC-005 明确写道"目标商品: 选择一件上架状态的种子商品（如 iPhone 15 Pro Max）"，并将执行下架操作。虽然清理责任要求"测试完成后立即将该商品重新上架"，但这**直接修改了种子数据的状态**。

**所在位置：** B-TC-005 测试数据和清理责任字段

**证据：**
- 用例文档开头声明"本轮新建测试数据，不修改种子数据"
- B-TC-005 的清理责任写道"测试完成后立即将该商品重新上架（点击'上架'按钮），恢复种子数据状态"

**影响：** 如果清理失败，种子数据被永久修改，影响所有依赖该商品的前台用例。

**严重度：** 中
**责任阶段：** 设计

**修改建议：**
1. **使用 B-TC-002 创建的测试商品**作为下架/上架操作的目标，而非种子数据商品
2. 更新 B-TC-005 的测试数据为："目标商品: B-TC-002 创建的'测试商品-自动化测试'（需先通过编辑将其状态改为'上架'）"
3. 这样即使清理失败，也只影响测试数据，不影响种子数据

---

### S-07：F-TC-025~F-TC-029 的清理责任标注为"记录订单最终状态"，未实现实际清理

**问题描述：** 5 条状态机用例的清理责任均为"记录订单最终状态"或"订单状态变更不可逆，记录最终状态"。这意味着测试产生的数据**永远不会被清理**。

**所在位置：** F-TC-025~F-TC-029 清理责任字段

**证据：** 订单状态一旦变为"已支付""已发货""已完成""已退款"，如果没有反向操作 API，这些订单将永久留在系统中。

**影响：** 多轮测试后系统中会积累大量脏数据，可能影响仪表盘统计数据和其他用例。

**严重度：** 低
**责任阶段：** 设计

**修改建议：**
1. 在用例中增加备注："本轮状态机测试产生的订单数据保留在系统中，不清理。后续轮次测试时需注意区分本轮数据与种子数据。"
2. 如果有数据库访问权限，记录清理 SQL 语句作为备用

### 5.3 放行建议

**🔴 不建议直接放行进入执行阶段。**

理由：
1. **B-01（API 造数方案未验证）是阻塞项**——5 条状态机 PO 级用例的前置条件完全依赖未验证的 API，如果方案不成立，本轮核心验证目标（状态机 5 迁移）将完全落空
2. **B-02（链式依赖）会导致用例互相污染**——不解决执行顺序和数据隔离问题，测试结果不可靠
3. **B-03（重复提交预期不确定）**——作为用户明确要求的验证项，不能以"探索性"方式执行

**建议执行路径：**
1. **第一步（解决 Blocking）**：
   - 执行 API 探针测试，验证订单状态修改 API 是否可用（预计 30 分钟）
   - 根据探针结果，确定造数方案并更新用例前置条件
   - 为 F-TC-026 和 F-TC-029 各自分配独立的"已支付"订单
   - 将 F-TC-020 的预期明确化
   - 将 F-TC-036 调整到执行顺序末尾
2. **第二步（解决 Should）**：
   - 修正 F-TC-013 的交叉引用
   - 明确 F-TC-022 的测试数据
   - 更新 B-TC-005/006 使用测试商品而非种子数据
3. **第三步（放行执行）**：
   - 解决上述问题后，46 条可直接执行的用例可先行执行
   - 状态机用例在造数方案验证通过后执行
