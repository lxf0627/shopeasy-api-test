## 一、业务目标理解

### 1.1 核心业务目标

普通用户（buyer 角色）能够独立完成从注册到售后的完整购物流程，涵盖 12 个主流程：

| 序号 | 主流程 | 业务目标 |
|------|--------|---------|
| 1 | 用户注册 | 新用户创建账号 |
| 2 | 用户登录 | 已注册用户认证进入系统 |
| 3 | 浏览商品与搜索 | 发现目标商品 |
| 4 | 商品详情与规格价格 | 了解商品信息、选择规格 |
| 5 | 加入购物车 | 将选中商品暂存 |
| 6 | 购物车管理 | 管理待购买商品 |
| 7 | 结算下单 | 确认订单信息并提交 |
| 8 | 订单查询与取消 | 跟踪订单状态、取消未支付订单 |
| 9 | 地址管理 | 维护收货地址 |
| 10 | 收藏管理 | 收藏/取消收藏感兴趣的商品 |
| 11 | 个人中心 | 管理个人信息和密码 |
| 12 | 用户登出 | 安全退出系统 |

### 1.2 涉及角色

| 角色 | 用户名 | 权限范围 | 来源 |
|------|--------|---------|------|
| 用户1 | buyer1（张三） | 前台全部功能，不可访问后台 | F-09, F-27 |
| 用户2 | buyer2（李四） | 前台全部功能，不可访问后台 | F-09 |
| 管理员 | admin | 前台全部功能 + 后台管理 | F-28, F-29 |
| 禁用用户 | disabled_user | 不可登录（403 Forbidden） | F-35 |

## 二、关键业务规则

### 2.1 规格-价格-库存联动规则（I-01, verified）

- 必须同时选择**所有规格维度**（如内存+颜色）后，价格/库存才会更新
- 仅选择一个维度时，价格/库存保持默认值不变
- "加入购物车"按钮在未选全规格时为 disabled 状态

**追溯：** 业务梳理 §2.4 步骤3、4（F-06, F-07）

### 2.2 购物车删除确认规则（I-02, verified）

- 购物车删除商品前弹出确认模态框（标题"提示"，内容"确定删除该商品？"）
- 模态框含"取消"和"确定"两个按钮
- 点击"取消"关闭模态框，不执行删除

**追溯：** 业务梳理 §2.6 步骤4、5（F-15, F-16）

### 2.3 订单取消确认规则（I-02, verified）

- 取消订单前弹出确认模态框（"确定取消该订单？"）
- 确认后状态从"待支付"变为"已取消"
- "取消订单"和"去支付"按钮消失

**追溯：** 业务梳理 §2.8.3 步骤1、3（F-21, F-22）

### 2.4 权限拦截规则

| 规则 | 描述 | 来源 |
|------|------|------|
| 未登录拦截 | 未登录点击"加入购物车"重定向到 /login，alert"请先登录" | F-08 |
| 后台访问拦截 | buyer1 访问 /admin 被重定向到首页 | F-27 |
| 禁用用户拦截 | disabled_user 登录返回 403 Forbidden | F-35 |
| 管理员前台入口 | admin 用户菜单多一项"管理后台" | F-28 |

### 2.5 订单状态机（已知状态）

已知状态（F-19）：待支付、已支付、已发货、已完成、已取消、已退款

已验证迁移：待支付 → 已取消（F-22）

待验证迁移（5条，**服务端源码已确认真实 API 端点**）：
1. 待支付 → 已支付：`POST /api/orders/:id/pay`
2. 已支付 → 已发货：`PUT /api/admin/orders/:id/ship`
3. 已发货 → 已完成：`PUT /api/orders/:id/confirm`
4. 待支付 → 已退款：`PUT /api/admin/orders/:id/refund`
5. 已支付 → 已退款：`PUT /api/admin/orders/:id/refund`

**重要**：`POST /api/orders` 创建订单时 `addressId` 为 Joi 必填字段。用例中原来推测的 `PUT /api/orders/{id}`、`PATCH /api/orders/{id}/status` 一律删除。

## 三、风险识别（8 维度核对）

### 3.1 正向维度

| 风险点 | 描述 | 优先级 |
|--------|------|--------|
| 注册→登录→浏览→加购→结算→下单 完整链路 | 核心购物流程的端到端验证 | PO |
| 收藏/取消收藏完整链路 | 收藏功能的双向操作 | P1 |
| 地址 CRUD 完整链路 | 新增/编辑/删除地址 | P1 |
| 个人信息修改保存 | 保存修改的响应与数据持久化 | P1 |

### 3.2 异常维度

| 风险点 | 描述 | 优先级 |
|--------|------|--------|
| 🔴 订单详情收货信息为空 | 结算页已选地址但详情页为空（S-01） | PO |
| 🔴 空地址下单 | 用户无收货地址时提交订单（Q-09） | PO |
| 🔴 重复提交订单 | 快速多次点击"提交订单"（B-R02） | PO |
| 🔴 库存不足场景 | 库存为0或数量超过库存（B-D03） | PO |
| 禁用用户登录 | disabled_user 返回 403 | P1 |
| 未选规格加入购物车 | 按钮 disabled 状态验证 | P1 |
| 结算页地址为空时提交 | 可能创建无效订单 | P1 |

### 3.3 边界维度

| 风险点 | 描述 | 优先级 |
|--------|------|--------|
| 注册用户名边界 | 3-50字符边界值 | P1 |
| 注册密码边界 | 至少6位边界值 | P1 |
| 订单备注边界 | 0/500字符边界 | P2 |
| 数量选择器边界 | 最小值1、最大值=库存 | P1 |
| 搜索框空搜索 | 空关键词搜索行为 | P2 |

### 3.4 权限维度

| 风险点 | 描述 | 优先级 |
|--------|------|--------|
| 未登录访问需登录功能 | 加入购物车、收藏、结算等 | PO |
| 普通用户访问后台 | /admin 及子路径拦截 | PO |
| 禁用用户登录拦截 | 403 Forbidden | P1 |
| 管理员前台功能一致性 | admin 前台操作与普通用户一致 | P2 |

### 3.5 状态维度

| 风险点 | 描述 | 优先级 |
|--------|------|--------|
| 🔴 订单状态机 5 条未验证迁移 | 待支付→已支付→已发货→已完成等 | PO |
| 购物车为空状态 | 空购物车的页面展示 | P2 |
| 登录/登出状态切换 | 导航栏变化验证 | P1 |
| 已收藏状态切换 | 收藏/取消收藏按钮状态 | P2 |

### 3.6 配置维度

| 风险点 | 描述 | 优先级 |
|--------|------|--------|
| 支付方式不明确 | 结算页未显示支付方式选择（I-07） | P2 |
| 前台分页大小 | 12条/页（已验证） | P3 |

### 3.7 数据一致性维度

| 风险点 | 描述 | 优先级 |
|--------|------|--------|
| 🔴 订单地址数据丢失 | 结算页有地址、详情页为空（S-01） | PO |
| 多商品结算金额计算 | 多件不同商品的合计准确性 | P1 |
| 同商品不同规格加购 | 不同规格是否作为独立 SKU | P1 |
| 下架商品对购物车的影响 | 前后台数据一致性（B-S03） | P1 |
| buyer2 流程一致性 | 与 buyer1 流程结果对比 | P1 |

### 3.8 网络与加载异常维度

| 风险点 | 描述 | 优先级 |
|--------|------|--------|
| 慢网络下加入购物车 | 重复点击防护 | P2 |
| 慢网络下提交订单 | 重复提交防护 | P2 |
| API 超时处理 | 页面是否有超时提示 | P3 |

## 四、测试策略说明

### 4.1 PO 级用例（必须通过）

本轮必须验证以下 4 类核心场景：

1. **订单详情收货信息为空的复现与根因定位**
   - 对比不同地址下单的结果
   - 核对订单创建 API 请求体中是否包含地址信息
   - 追溯：业务梳理 §2.7 步骤6 vs §2.8.2 步骤1（F-17 vs F-20）

2. **订单状态机 5 条未验证迁移路径**（服务端源码已确认真实 API 端点）
   - 逐条验证：待支付→已支付（`POST /api/orders/:id/pay`）、已支付→已发货（`PUT /api/admin/orders/:id/ship`）、已发货→已完成（`PUT /api/orders/:id/confirm`）、待支付→已退款（`PUT /api/admin/orders/:id/refund`）、已支付→已退款（`PUT /api/admin/orders/:id/refund`）
   - 订单创建时需传入 addressId（Joi 必填校验）
   - 追溯：业务梳理 §2.8（B-S01）

3. **核心 CRUD 保存/确认响应**
   - 前台：地址新增/编辑/删除、个人信息保存、密码修改
   - 追溯：业务梳理 §2.9、§2.11

4. **异常场景优先覆盖**
   - 空地址下单（🔴最高优先级）
   - 重复提交订单
   - 库存不足

### 4.2 测试数据策略

- **本轮新建测试数据**，不修改种子数据
- 新增商品：通过后台"新增商品"创建测试专用商品
- 新增订单：通过前台流程创建测试专用订单（POST /api/orders，需传入 addressId）
- 新增地址：通过个人中心创建测试专用地址
- 每条用例明确清理责任

### 4.3 buyer2 一致性覆盖

- 使用 buyer2（李四）完整走一遍前台 12 个主流程
- 对比 buyer1 和 buyer2 的页面展示、功能响应、数据一致性
- 重点关注：地址隔离、订单隔离、收藏隔离

### 4.4 探索性场景标注

以下场景因缺乏已验证事实支持，标记为探索性场景：
- 支付方式选择逻辑（I-07, candidate）
- 下架商品对购物车的影响（B-S03, 未验证）
- 购物车空态展示（B-S02, 未验证）
- 修改密码完整流程（未验证）
