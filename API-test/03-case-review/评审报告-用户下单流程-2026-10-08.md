## 2. 必须修改项

### 问题 1：场景描述与实际步骤不一致

| 字段 | 内容 |
|------|------|
| **编号** | MUST-001 |
| **描述** | TC-POS-001 场景描述写"创建订单并支付"，但实际步骤只到查询订单详情，没有支付步骤 |
| **位置** | 用例文档 TC-POS-001 |
| **证据** | 场景描述："用户登录后，将有规格商品加入购物车，创建订单并支付"；步骤6为"查询订单详情"，预期5为"status=pending"（待支付状态） |
| **影响** | 执行者会困惑是否需要执行支付步骤，测试覆盖不完整 |
| **严重度** | 必须修改 |
| **责任阶段** | 用例设计 |

**返修方向：**
- 方案A：修改场景描述为"创建订单"，删除"并支付"
- 方案B：在步骤6后增加支付步骤，预期验证status变为paid

### 问题 2：多个场景缺少前置数据具体来源

| 字段 | 内容 |
|------|------|
| **编号** | MUST-002 |
| **描述** | TC-EXC-005、TC-STS-001、TC-STS-002、TC-STS-003、TC-STS-004、TC-AUTH-004 等场景的前置条件或测试步骤中引用了不确定的订单ID或地址ID |
| **位置** | 用例文档多个场景 |
| **证据** | TC-EXC-005步骤2添加购物车成功，但buyer2是否有地址未说明；TC-STS-001前置"存在paid状态的订单"但未说明如何创建；TC-AUTH-004引用"{buyer1的订单id}"但未说明来源 |
| **影响** | 执行者无法独立执行这些场景，需要依赖其他场景的执行结果或额外准备数据 |
| **严重度** | 必须修改 |
| **责任阶段** | 用例设计 |

**返修方向：**
- 为每个场景明确前置数据的创建方式
- 或者在场景依赖关系中明确说明执行顺序

### 问题 3：边界测试预期不确定

### 问题 4：buyer2账号前置条件不明确

| 字段 | 内容 |
|------|------|
| **编号** | MUST-004 |
