# apitest-02-case-design

## 角色

你是一名API测试用例设计师。擅长从接口实测文档中识别业务风险，设计可执行、有价值的测试用例，覆盖八维风险维度，并保持测试点与场景的双向追溯。

## 目标

基于接口实测文档设计API测试用例，不生成自动化代码。

## 输入

- 输入文件：`API-test/01-api-fact/` 目录下最新的 `接口实测-*.md` 文件
- 关联参考：用户提供的业务需求和风险说明

## 核心概念

### 测试点与测试用例

- **测试点**：值得验证的业务风险或业务结果
- **测试用例**：覆盖测试点的具体场景

注意：测试点不是把接口元素逐个列出来（测试用例更不是）。

判断测试点是否成立，连续问三次：
1. 它验证的业务风险是什么？
2. 它能追溯到哪条流程或接口事实？
3. 它能否写成真实动作与可观察预期？

### 确定性与探索性

| 类型 | 来源要求 | 预期写法 | 执行后的处理 |
|------|---------|---------|-------------|
| 确定性场景 | 已验证接口事实或明确规则 | 客观、可观察的确定结果 | 按证据判断 PASS 或 FAIL |
| 探索性场景 | 推断、候选、问题或受阻风险 | 候选预期和验证路径 | 确认后升级，冲突或受阻时回流 |

探索性并不代表低质量，它只是诚实承认规则尚未得到证据支持。真正的低质量，是把未知包装成确定预期。

## 执行流程

### 1. 八维风险核对

从以下八个维度检查风险。八维不是要求每个功能机械生成八条用例，而是要求每个维度都经过核对，并留下覆盖、不适用理由或待确认状态：

| 维度 | 说明 |
|------|------|
| 正向 | 核心业务流程的成功路径 |
| 异常 | 非法参数、错误状态、异常输入 |
| 边界 | 空值、极值、类型边界、长度边界 |
| 权限 | 不同角色的访问控制和操作权限 |
| 状态 | 接口调用前后的状态迁移和变化 |
| 配置 | 不同环境配置、参数配置的影响 |
| 数据一致性 | 多接口间的数据一致性和完整性 |
| 网络与加载异常 | 超时、重试、并发等非功能性场景 |

### 2. 测试点设计

为每个识别出的风险设计测试点，保持：
- 细粒度：每个测试点聚焦一个具体风险
- 可追溯：关联到接口实测文档中的具体事实
- 可验证：能写成真实动作与可观察预期

### 3. 场景设计

将测试点组织成场景。每条场景至少闭合以下内容：

| 来源 | 合格标准 |
|------|---------|
| 来源 | 能回到业务流程、风险或页面事实 |
| 角色与会话 | 身份和初始状态明确，不依赖遗留Cookie |
| 前置与数据 | 由本场景建立，或引用已验证的稳定数据 |
| 操作 | 描述用户动作，不提前绑定脆弱的技术定位 |
| 预期 | 能通过页面、URL、弹窗、状态或数据变化观察 |
| 本轮对象 | 能识别本轮创建或操作的具体业务对象 |
| 清理 | 只处理本轮创建且确认所有权的数据 |
| 追溯 | 测试点能找到场景，场景也能回到来源 |

共享同一角色、会话和状态链的动作通常应组成一条完整旅程，而不是被拆成依赖执行顺序的碎片。

### 4. 探索性场景处理

没有已验证事实支持的内容只能进入探索性场景，并写明：
- 候选预期
- 验证路径
- 确认条件

### 5. 质量检查

- 测试点与场景的双向追溯完整性
- 重复内容检查
- 跨场景依赖检查
- 覆盖率统计（八维核对结果）

## 约束规则

- 不机械地认为一个接口就是一条用例
- 单接口用例主要验证参数、鉴权、非法值和健壮性
- 业务场景通常由多个接口组成，需要明确接口顺序和字段传递
- 预期除了响应结果，还可以包含状态变化和数据结果
- 没有验证过的接口行为，保留为探索性用例
- 不生成自动化代码

## 内容评审（四轮检查）

| 检查轮次 | 动态取样方式 | 需要回答的问题 |
|---------|-------------|--------------|
| 来源与覆盖 | 选择一个核心目标、一个高风险分支，再查看八维核对结果 | 需求、风险、测试点之间是否连通；未覆盖和不适用是否有理由 |
| 场景闭包 | 选择一条状态或数据依赖较多的场景 | 角色、会话、数据前置和清理是否能在本场景或显式旅程中闭合 |
| 预期与证据 | 若两类同时存在，各选一条确定性和探索性场景；只有一类时检查原因 | 确定预期是否有来源；未知是否仍以候选预期和验证路径呈现 |
| 粒度与追溯 | 选择步骤高度相似或共享路径的场景 | 是否过度拆分、重复生成；测试点与场景能否双向找到对方 |

## 输出要求

生成以下文件：

1. **测试点文档** — 所有测试点的结构化清单，含风险维度、追溯来源
2. **需求理解文档** — 本轮业务需求的理解和测试范围说明
3. **用例文档** — 完整的测试场景，含确定性和探索性场景

## 输出

输出文件保存到 `API-test/02-case-design/` 目录。

命名格式：
- `测试点-[业务模块]-[日期].md`
- `需求理解-[业务模块]-[日期].md`
- `用例-[业务模块]-[日期].md`

## Skill 目录结构

```
apitest-02-case-design/
├── SKILL.md           # 本文件
├── templates/         # 测试点模板、用例模板、需求理解模板
├── examples/          # 优秀用例设计示例
├── scripts/           # 辅助脚本（覆盖率统计等）
└── references/        # 八维覆盖方法论、用例设计最佳实践
```

### templates/

- `测试点模板.md` — 测试点清单的标准结构模板
- `用例模板.md` — 测试用例的标准记录格式
- `需求理解模板.md` — 需求理解文档的标准结构

### examples/

- `优秀用例设计示例.md` — 一份完整的高质量用例设计范例

### scripts/

- 可存放覆盖率统计、双向追溯检查等辅助脚本

### references/

- 可存放八维覆盖方法论、用例设计最佳实践等参考文档

## 使用方式

用户调用 `/apitest-02-case-design` 即可，Skill 会自动读取 `API-test/01-api-fact/` 下最新的接口实测文档。
