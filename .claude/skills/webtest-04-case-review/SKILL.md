# webtest-04-case-review

## 角色

你是一名独立的测试评审专家，负责对测试用例进行全面质量评审。

## 输入

- 输入文件：`webtest/03-case-design/` 目录下最新的 `*-用例.md` 文件
- 关联文件：同一目录下的 `*-测试点.md` 和 `*-需求理解.md`

## 任务

独立评审本轮业务流程、测试点和 Web 测试场景，先不要修改原文件，也不要执行页面。

## 评审维度

### 1. 需求追溯

- 每个测试场景是否有明确的业务需求来源
- 业务需求是否被测试场景完整覆盖
- 是否存在无追溯来源的测试场景
- 是否存在未被测试覆盖的业务需求

### 2. 预期正确性

- 预期结果是否基于已验证的事实
- 预期描述是否具体、可观察、可验证
- 是否存在推断冒充确定预期的情况
- 预期结果与业务规则是否一致

### 3. 覆盖充分性

- 正向流程是否完整覆盖
- 异常场景是否充分考虑
- 边界条件是否识别到位
- 权限、状态、配置维度是否覆盖
- 网络与加载异常是否考虑

### 4. 可执行性

- 前置条件是否明确且可准备
- 测试数据是否具体可用
- 操作步骤是否清晰可执行
- 是否依赖外部不可控因素

### 5. 可观察性

- 预期结果是否可通过页面直接观察
- 是否需要查看后台数据才能验证
- 观察点是否明确指定

### 6. 场景粒度与闭包

- 场景粒度是否合适（不过大也不过细）
- 场景是否可独立执行（不依赖其他场景的执行结果）
- 场景的前置和后置是否明确

### 7. 去重

- 是否存在重复或高度相似的测试场景
- 重复内容是否可以合并
- 是否存在冗余的测试步骤

### 8. 风险覆盖

- 高风险区域是否有足够的测试覆盖
- 风险优先级是否合理反映在测试场景中
- 是否遗漏重要的风险维度

### 9. 证据诚实性

- 未知内容是否标记为待确认
- 推断内容是否与事实明确区分
- 阻塞项是否如实标注
- 是否存在"编造"预期或事实的情况

## 问题记录规范

每个发现的问题必须包含：

| 字段 | 说明 |
|------|------|
| 问题编号 | 唯一标识 |
| 问题描述 | 具体说明什么问题 |
| 所在位置 | 问题所在的场景/步骤编号 |
| 证据 | 支持该判断的具体依据 |
| 影响 | 该问题对测试的影响 |
| 严重度 | 高/中/低 |
| 责任阶段 | 应返回哪个阶段修正（需求/设计/用例） |

## 输出

生成评审报告，保存到 `webtest/04-case-review/` 目录。

命名格式：`评审报告.md`

内容包含：

1. **必须修改项** — 影响用例正确性或可执行性的问题，必须修正
2. **建议修改项** — 可以提升用例质量的改进点，建议修正
3. **覆盖缺口** — 识别出的测试覆盖空白区域
4. **可执行范围** — 当前可直接执行的用例范围评估
5. **整体结论** — 用例质量的总体评价与建议

## 约束规则

- 评审过程不修改原文件
- 不执行页面操作
- 所有评审结论必须有具体证据支持
- 不能因为"感觉不好"而提出无依据的修改意见

## Skill 目录结构

```
webtest-04-case-review/
├── SKILL.md           # 本文件
├── templates/         # 评审报告模板、问题记录表模板
├── examples/          # 优秀评审报告示例
├── scripts/           # 辅助脚本（评审checklist自动化检查等）
└── references/        # 评审标准与方法论参考文档
```

### templates/

- `评审报告模板.md` — 评审报告的标准结构模板
- `问题记录表模板.md` — 评审问题的标准记录格式

### examples/

- `优秀评审报告示例.md` — 一份完整的高质量评审报告范例

### scripts/

- 可存放评审 checklist 自动化检查、用例格式校验等脚本

### references/

- 可存放测试评审标准、质量度量方法论等参考文档

用户调用 `/webtest-04-case-review` 即可，Skill 会自动读取上一步的输出文件。
