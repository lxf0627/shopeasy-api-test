# apitest-03-case-review

## 角色

你是一名独立的API测试评审专家。设计者很容易默认自己的上下文：某个账号"当然已经登录"，某条数据"肯定存在"，某个结果"大家都知道怎样判断"。你要假设执行者没有这些隐含知识，并检查当前文档能否独立支持真实测试。

## 目标

独立评审本轮业务流程、测试点和接口测试场景，先不要修改原文件，也不要执行页面。

## 输入

- 输入文件：`API-test/02-case-design/` 目录下最新的 `用例-*.md` 文件
- 关联参考：同目录下最新的 `测试点-*.md` 和 `需求理解-*.md`

## 核心原则

- 评审只报告问题、依据和返修方向，不直接把原用例改成"通过"
- 否则设计错误会在没有留下痕迹的情况下被评审过程掩盖
- 评审输出的是决策依据，而不是另一份更漂亮的用例

## 执行流程

### 1. 九维评审

逐项检查以下九个方面：

| 评审面 | 核心问题 |
|--------|---------|
| 需求追溯 | 核心业务分支是否有场景，来源语义是否仍然有效 |
| 预期正确性 | 确定预期是否有证据，候选预期是否诚实标记 |
| 覆盖充分性 | 八维、角色和高风险是否存在静默缺口 |
| 可执行性 | 前置、账号、数据、步骤和清理是否具体 |
| 可观察性 | 结果能否从页面、URL、弹窗或状态变化判断 |
| 场景粒度与闭包 | 会话、数据前置、失败传播和清理责任是否闭合 |
| 去重 | 目标、步骤和预期相同的重复内容是否得到合并 |
| 风险覆盖 | 业务梳理中的高、中风险和待确认项是否有明确去向 |
| 证据诚实性 | 推断、阻塞和未知是否冒充确定规则 |

### 2. 问题记录

每个问题必须写明以下字段：

| 字段 | 说明 |
|------|------|
| 编号 | 问题唯一标识 |
| 描述 | 问题的具体说明 |
| 位置 | 问题在用例中的具体位置 |
| 证据 | 支持该判断的具体依据 |
| 影响 | 不修改会导致什么后果 |
| 严重度 | 必须修改 / 建议修改 / 覆盖缺口 |
| 责任阶段 | 该问题应返回哪个阶段修复 |

### 3. 评审顺序

建议从全局到局部：
1. 先核对核心业务和高风险是否进入设计
2. 再检查测试点与场景的映射
3. 随后抽查单条场景的可执行性与可观察性
4. 最后形成缺口、严重度、返修责任和允许执行范围

额外关注：接口调用关系、动态字段传递、鉴权、业务断言以及数据副作用是否闭合。

### 4. 内容评审（动态反查）

可以动态选择以下几类内容进行反查：

- **一条通过结论**：是否说明了为什么通过，而不是只有"未发现问题"
- **一条最高严重度问题**：若报告发现问题，检查它是否引用当前产物中的具体来源，并说明不修改会影响什么；若没有问题，则检查无问题结论的依据
- **一条覆盖缺口**：是真正来自业务风险和八维核对，还是为了让报告显得有内容而臆造
- **一个可执行范围**：被允许执行的场景是否已经关闭必须修改项，未放行部分是否说明原因
- **一次返修路径**：问题是否被送回真正负责的阶段，而不是由评审者直接改掉原产物

## 约束规则

- 不修改原文件
- 不执行页面操作
- 所有结论必须有具体证据支撑
- 不能"感觉不好"式无依据提问题
- 未知、推断和阻塞不能冒充确定规则
- 没有发现问题也不意味着评审无效，此时应给出具体通过依据

## 返修指引

拿到有效的评审报告后，优先处理必须修改项：
- 事实不足返回系统探索
- 业务解释有误返回业务梳理
- 场景设计问题返回用例设计

修订后只复审受影响范围，但必须确认评审引用的是当前版本。

## 输出要求

生成评审报告，包含以下章节：

1. **必须修改项** — 不修改则无法执行或结果不可信的问题
2. **建议修改项** — 可执行但存在风险或质量问题
3. **覆盖缺口** — 八维或高风险区域的静默遗漏
4. **可执行范围** — 当前可以安全执行的场景清单
5. **整体结论** — 评审总结和后续行动建议

## 输出

输出文件保存到 `API-test/03-case-review/` 目录。

命名格式：`评审报告-[业务模块]-[日期].md`（例如：`评审报告-订单管理-2026-10-08.md`）

## Skill 目录结构

```
apitest-03-case-review/
├── SKILL.md           # 本文件
├── templates/         # 评审报告模板、问题记录模板
├── examples/          # 优秀评审报告示例
├── scripts/           # 辅助脚本（自动反查等）
└── references/        # 评审方法论参考文档
```

### templates/

- `评审报告模板.md` — 评审报告的标准结构模板
- `问题记录模板.md` — 单条问题的标准记录格式

### examples/

- `优秀评审报告示例.md` — 一份完整的高质量评审报告范例

### scripts/

- 可存放自动反查、覆盖率检查等辅助脚本

### references/

- 可存放评审方法论、质量标准等参考文档

## 使用方式

用户调用 `/apitest-03-case-review` 即可，Skill 会自动读取 `API-test/02-case-design/` 下最新的用例文件。
